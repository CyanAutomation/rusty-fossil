# ADR 0009: Run only the fixed synthetic worker in Phase 2B

- Status: Accepted
- Date: 2026-11-21

## Context

Phase 2B validates the host-to-container lifecycle, not coding behavior. Interpreting task prompts as shell or command input would turn Queue content into host execution authority and widen the review surface before repository and credential boundaries exist.

## Decision

The worker image is built from `Dockerfile.synthetic-worker` and contains one Rust executable with a closed set of six scenarios: success, controlled failure, timeout, cancellation, bounded output, and unexpected termination. The supervisor receives the scenario from its own startup configuration. Its IPC protocol contains only a canonical run ID; no request can select an image, entrypoint, command, mount, Docker flag, or scenario. Queue task prompts remain opaque stored metadata.

The trusted release image is addressed by digest under `ghcr.io/cyanautomation/rusty-fossil-synthetic-worker`. Local CI can use a Docker image ID generated by building the checked-in Dockerfile. The supervisor never pulls an image based on run input. If the configured immutable image is unavailable, execution fails closed.

Containers run as UID/GID 65532 with a read-only root filesystem, all capabilities dropped, `no-new-privileges`, no network, no ports, no devices, no host mounts, no host PID/IPC/UTS namespace, and Docker's normal seccomp profile. CPU, memory and swap, PIDs, tmpfs, runtime, stop grace, and Docker json-file logs are bounded. The supervisor inspects effective Docker configuration before start and stops if a required control is missing.

Docker Engine access belongs only to the separate `fossil-supervisord` process. It exposes authenticated local IPC rather than a Docker API proxy. The controller receives only a Unix socket and a private IPC token when an operator explicitly wires the non-production handoff.

## Consequences

- No Pi CLI, repository checkout, Git operation, model call, publication, or task-derived command runs in Phase 2B.
- The worker image is intentionally disposable and not useful for production coding work.
- The supervisor's Docker socket remains a powerful host capability and must be limited to the dedicated trusted account/service.
- Rootless Docker is preferred; the container itself never receives the Engine socket.
