# Compatibility inventory

## Scope

Rusty-Fossil is a clean-room Rust controller, not a source-level port of Kaseki-Agent. Kaseki test suites were inspected as behavioral evidence: `src/integrations/soyuz/SoyuzAdapter.test.ts`, `src/job-persistence-manager.test.ts`, `src/job-scheduler.test.ts`, and `src/kaseki-api-routes.test.ts`. Their TypeScript internals are not run against Rust. Contract-v1 behavior is represented by Rust types, independent JSON fixtures, SQLite tests and local HTTP mocks.

The inspected Kaseki operation index links to an OpenAPI 3.1 document and advertises client submission, run status/retry/cancellation, worker diagnostics, logs, artifacts, webhooks, gateway diagnostics, and callback operations. Rusty-Fossil does not proxy or implement those Kaseki routes. In particular, this service has no `POST /api/v1/runs`, `POST /api/v1/runs/local`, or independent execution route.

## Preserved behaviors and explicit limits

- Soyuz's canonical UUID is the only deduplication and run-identity key. Display IDs and Queue leases never authorize work.
- The normalized `publishMode` is preserved; omitted values resolve to `pr`. Explicit non-`pr` modes are test-only exceptions under the shared publication policy. This controller does not publish to GitHub.
- Queue data alone cannot authorize a claim/start; canonical state and private-field proofs are required.
- A failed or uncertain Soyuz request does not enable direct local execution.
- Unsupported normalized run settings fail closed rather than being discarded.
- The production `main` does not construct the coordinator, poll Queue, replay callbacks, or attach the supervisor IPC client. Deployment of `fossil-supervisord` alone does not consume work.
- Production polling, recovery supervision, callback replay and Senku inference are not started from the service binary. This keeps this implementation from consuming production messages or invoking paid inference.
- SQLite state is a single-host journal, not a multi-host scheduler. Cross-host takeover, claim renewal, live DLQ behavior, and live Queue producer content type remain unverified or deferred.
- This development host cannot access its Docker socket; the real Docker test is delegated to Docker-enabled CI and has not been observed locally.
- No Raspberry Pi hardware run has been performed; ARM64 cross-build is not a substitute for testing host cgroups, rootless Docker, memory pressure, disk limits or restart recovery on a Pi.

## Follow-on evidence

Phase 2C-A completion still requires a supervisor-enabled Pi image/resource profile, integration of the repository-preparation library in a no-Docker-socket preparation process, enforced worker egress, supervisor-issued broker capabilities, supervisor-staged read-only prompt delivery, durable result/callback handling, and end-to-end recovery testing. The broker prototype has request and token bounds but no cost-based dollar ceiling; no Cloudflare inference was made. The worker reads a fixed-path payload file, but the supervisor does not yet prepare or mount it. The generalized ARM64 host inventory and preflight are in [ARM64 host compatibility](ARM64-HOST-COMPATIBILITY.md) and [validation](ARM64-HOST-VALIDATION.md); host and account identifiers are omitted. The preflight did not establish a dedicated service identity, effective SSH policy, deployed Compose boundary, approved non-production gateway, spend limit, or enforced egress. No inference was made. Before runtime rollout, separately review the Kaseki-owned Senku credential and non-production Queue/DLQ configuration.
